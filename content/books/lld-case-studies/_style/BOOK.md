# LLD Case Studies: Production Systems — rules for this book

Read `content/_style/STYLE.md` and `content/_style/AUTHORING.md` first. This file adds what is specific to **LLD Case Studies: Production Systems** (`lld-case-studies`). Where it differs from STYLE.md, this file wins for this book.

## Who it is for
a backend engineer who knows Java and Node.js basics and wants production-quality LLD for interviews and real work. Write for that reader: say what they already know, and never assume more.

## What the examples run on — one language per layer
Profile: `mixed`. Every system is designed across ALL layers, each in a fixed language:
| Layer | Language | How it runs |
|---|---|---|
| Domain model, classes, patterns, state machines, in-memory concurrency | **Java 17** | `.java`, `run: "captured"` (`java File.java`, JDK only) |
| Database schema, queries, transactions, locking | **Node.js 20 + `pg` on a REAL PostgreSQL 18** | `.mjs`, `run: "captured"`, `"needs": ["postgres"]` |
| Backend REST API (routes, controllers, services, repositories, validation, errors) | **Node.js 20 + Express 5 (+ `pg`, `zod`)** | `.mjs`, `run: "captured"`, `"needs": ["postgres"]` when it touches the DB |
| Frontend (screens, components, UI state, API client) | **React (JavaScript)** for components; **plain JavaScript** for state logic | components: `.jsx`-style code in a `.js` file, `lang: "js"`, `run: "static"`, `illustrative: true`; state reducers / API-client logic: pure `.mjs`, `run: "browser"` (runs in the page) |

### Java rules
- One source file per example; **file name = its public class**, and that FIRST class holds `main`; other types package-private. Java 17 only (no switch pattern matching, record patterns, virtual threads, `SequencedCollection`). Lines <= 80 columns.
- Deterministic output: no `HashMap`/`HashSet` order (use `LinkedHashMap`/`TreeMap`/sort), no clocks (inject a fixed `Clock` or pass times in), seeded randoms only, threads joined before printing.
- Money is `long` minor units (paise/cents), never `double`. Ids are `String`s generated by an injected counter in demos (`"BK-1"`, `"BK-2"`).

### Node.js + PostgreSQL rules
- ES modules (`.mjs`), Node 20. Allowed libraries (already installed): `express` 5, `pg`, `zod`, `nanoid` (avoid in output: random), `helmet`, `cors`, `morgan` (no output in captures).
- DB snippets: `import pg from 'pg'; const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });`. The database starts EMPTY each run: create the schema in the snippet (`CREATE TABLE ...`), seed fixed rows, run the queries, print results, then `await pool.end()` so the process exits.
- Show real database guarantees and PROVE them in the output: primary keys, `UNIQUE`, `CHECK`, foreign keys, partial unique indexes, `SELECT ... FOR UPDATE` inside `BEGIN/COMMIT`, `ON CONFLICT`, optimistic locking with a `version` column, idempotency-key tables. Print the Postgres error `code` (e.g. `23505` unique violation, `23P01` exclusion violation) when demonstrating a refused write.
- Concurrency in SQL: simulate two users with two clients from the pool running in parallel (`Promise.all`) and print only deterministic final state (who won is decided by locks/constraints, not timing: e.g. both try, exactly one row exists after).
- Deterministic output: fixed timestamps as literals (`'2026-01-15 10:00+00'`), `ORDER BY` on every multi-row query, print `rows` with `console.table` NOT allowed (width varies): print JSON or formatted lines.
- API snippets: build the Express app with layers (router → controller → service → repository) in ONE file, `app.listen(0)`, call it with `fetch` for the happy path AND at least one failure (validation 400, conflict 409, not found 404), print `status` + JSON body, then close the server and the pool. Error-handling middleware maps domain errors to HTTP codes; validate bodies with `zod`; mutation endpoints that can be retried (payments, bookings, orders) accept an `Idempotency-Key` header.
- Snippets may be up to 90 lines when they have a `walk` (4 to 7 steps); every line <= 80 columns.

### Frontend rules
- The frontend page designs the UI as LLD: screens, component tree, which component owns which state, the API client, loading/error/empty states, optimistic updates and how double-submits are prevented. Use a `flow` hero for the component tree or a `seq` hero for the end-to-end request (Browser → API → Service → DB).
- One `.mjs` `run: "browser"` example of pure UI logic (a reducer or state machine for the screen, or an API client with retry/idempotency) that prints its transitions; plus one React component file shown statically (`illustrative: true`).

## The template every system chapter follows
Full systems (c02 to c13) have 8 pages, in this order; each page builds on the previous page's names:
1. **Requirements and Scope** — functional requirements, non-functional (consistency, latency, scale assumptions stated as assumptions), actors, use cases, what is OUT of scope. Hero: use-case flow. Code optional (a Java `enum` of use cases or a requirements-check), quiz on a scoping decision.
2. **Domain Model and Class Diagram** — entities, value objects, enums, relationships and multiplicities, using the class names the learner listed. Hero: class diagram as a `flow` (nodes = classes, `sub` = key fields/methods, edges labelled has-a/is-a/uses). Code: the Java model (records/enums/classes) with invariants.
3. **Core Design in Java** — the main service/manager classes, the design patterns used (name them, say why), interfaces for every swappable policy (strategy for pricing/allocation/scheduling, etc.). Two Java files: the core flow and one extension via a new strategy without editing old code.
4. **Key Flows and State Machine** — the lifecycle of the central entity as a state machine (Java `enum` with allowed transitions, illegal transitions rejected) and the main sequence (`seq` hero).
5. **Concurrency and Edge Cases** — what goes wrong with two users at once, and the fix in Java (locks, `ConcurrentHashMap`, atomic compare-and-set, holds with expiry) plus the edge cases (failures, timeouts, partial payments, cancellations). Prove the race and the fix with deterministic output.
6. **Database Schema and Queries** — PostgreSQL tables mapped from the Java model (snake_case tables/columns, `BIGINT` money in minor units, `TIMESTAMPTZ`, enums as `TEXT` + `CHECK`), keys, indexes for the main queries (say which query each index serves), constraints that enforce the invariants, and the critical transactional query (e.g. lock a seat, reserve a slot, deduct stock). Real run on PostgreSQL.
7. **Backend API in Node.js** — REST endpoints table (method, path, request, response, errors), Express app with layered structure, validation, error mapping, idempotency, transaction in the service. Real run on PostgreSQL with happy path + failures.
8. **Frontend Design and End-to-End Flow** — screens and component tree, UI state, API client, double-submit protection, error states; the end-to-end sequence; and 2 to 3 interview follow-ups (scale it, add a feature) in `points`/`pitfalls`.

Core systems (c14 to c21) have 6 pages: 1 Requirements and Scope; 2 Class Design (Java, class diagram hero); 3 Core Implementation in Java (complete, production-quality, with the main algorithm); 4 Concurrency and Thread Safety (Java); 5 Extensibility and Configuration (patterns: strategy/decorator/chain/builder; adding a new provider/policy without edits); 6 Node.js Service and Interview Follow-ups (the component exposed or used in a Node.js service — e.g. rate-limiter middleware, pub-sub with an outbox table on PostgreSQL, retrying fetch client against a local Express server that fails on purpose — plus interview follow-ups).

## Accuracy
- A wrong page is worse than a short one. Every behaviour claim about Java, Node, Express or PostgreSQL must be proven by captured output or be standard stable behaviour of those versions.
- No invented statistics, company internals, prices, limits or quotes. Do not claim how a real company (Uber, BookMyShow, Stripe...) builds its system; say "a typical design".

## Terms and spellings
- Name each system exactly as its chapter title. Layers: **domain model**, **service layer**, **repository**, **controller**, **API**, **frontend**.
- SQL: snake_case tables and columns (`parking_spot`, `amount_minor`); JSON: camelCase (`amountMinor`); Java: camelCase fields.
- **Idempotency-Key** (HTTP header), **optimistic locking**, **pessimistic locking (`SELECT ... FOR UPDATE`)**, **hold** (a temporary reservation with an expiry).
- **Inline code in `points`, `pitfalls`, `idea` and captions: at most 24 characters per backtick span** (a class or method name, not an expression). Long inline code cannot wrap and overflows the 4-column points layout. Put expressions in the code examples instead.
- **No backticks inside `table` hero cells or `head`** (they render as plain text).
